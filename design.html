Project 4: Load Balancer Design

Request queue, firewall check, server processing, and elastic capacity

Simulation workflow

A switch preloads requests and routes each request through an IPv4 firewall to one of two independent load balancers. The processing and streaming balancers each own a FIFO queue, server pool, scaling cooldown, and statistics; both advance once on each shared clock cycle.

Component responsibilities

  • Request stores source/destination IP, service time, and job type.
  • IPBlocker parses IPv4 addresses and checks exact/CIDR ranges before queue admission.
  • WebServer owns at most one active request and reports completion after its service cycles.
  • Switch generates requests, applies the IP blocker, routes by job type, advances both balancers on the shared clock, and reports combined/per-balancer statistics.
  • Each LoadBalancer owns one job type's FIFO queue and servers and scales independently.
  • Config parses validated settings; main combines configuration, prompts, and CLI overrides before constructing the switch.

The public interfaces make the ownership and one-cycle processing contract explicit. Helper methods are private to the component that owns the relevant state.

Cycle order: the switch generates/filter arrivals and routes each accepted request → check each balancer's independent scaling cooldown → advance already-busy servers in both balancers → record completions → dispatch each FIFO queue to its own idle servers → increment the shared completed-cycle count. Newly assigned requests start ticking next cycle. For example, a five-cycle request dispatched after the cycle-0 processing step gets its five ticks in cycles 1 through 5 and then becomes idle. Both independent balancers participate in every cycle, keeping their simulation clocks synchronized.

Scaling and reporting

The user's starting server count is total capacity. It is split evenly between two independent balancers, assigning an odd extra server to P; at least two starting servers are required. Each type is queued FIFO and handled only by its own servers. The P and S balancers independently compare their queue sizes with their own capacities and independently enforce the configured cooldown. Each balancer scales up strictly above 80 waiting requests per server and scales down strictly below 50. Their combined capacity respects the configured total maximum/minimum, each keeps its reserved minimum of at least one server, and only idle servers are removed. Both report generated, accepted, blocked, completed, queued, active, and scaling statistics.

Verbose mode logs completions, blocked requests, server scaling, and periodic queue/server snapshots. It omits routine accepted/dispatched request events, which can overwhelm a high-volume log. Quiet mode keeps console output to start/end summaries. Both modes write run statistics to the configured log, and console-only ANSI colors never enter the log file. End-of-run reporting separates queued and active requests from completed requests.
