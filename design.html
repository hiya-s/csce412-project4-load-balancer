Project 4: Load Balancer Design

Request queue, firewall check, server processing, and elastic capacity

Simulation workflow

The simulation preloads a FIFO queue, admits random arrivals after an IPv4 block check, assigns work to idle servers, and periodically evaluates capacity.

Component responsibilities

  • Request stores source/destination IP, service time, and job type.
  • IPBlocker parses IPv4 addresses and checks exact/CIDR ranges before queue admission.
  • WebServer owns at most one active request and reports completion after its service cycles.
  • LoadBalancer owns the FIFO queue, server pool, clock, counters, logger, and scaling policy.
  • Config parses validated settings; main combines configuration, prompts, and CLI overrides.

Method design: inputs, outputs, and responsibilities

The public interfaces make the ownership and one-cycle processing contract explicit. Helper methods are private to the component that owns the relevant state.

Cycle order: generate/filter arrivals → check scaling/cooldown → dispatch requests from the queue front to idle servers → advance each busy server by one cycle → record completions → increment completed-cycle count. An assigned five-cycle request is ticked on five successive cycles and becomes idle after the fifth tick.

Scaling and reporting

At most one server is added or removed per scaling check. The queue thresholds are strict: scale up above 80 waiting requests per server, and scale down below 50. A configurable cooldown separates successful changes. Only idle servers are removed, with a configurable minimum pool size.

Verbose mode logs meaningful request and scaling events; quiet mode keeps console output to start/end summaries. Both modes write run statistics to the configured log. End-of-run reporting separates queued and active requests from completed requests.
