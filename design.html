Project 4: Load Balancer Design

Request queue, firewall check, server processing, and elastic capacity

Simulation workflow

The simulation preloads separate processing and streaming FIFO queues, routes random arrivals after an IPv4 block check, assigns work only to matching idle servers, and scales each pool independently.

Component responsibilities

  • Request stores source/destination IP, service time, and job type.
  • IPBlocker parses IPv4 addresses and checks exact/CIDR ranges before queue admission.
  • WebServer owns at most one active request and reports completion after its service cycles.
  • LoadBalancer routes each accepted request to a P or S FIFO queue and scales the matching server pool.
  • Config parses validated settings; main combines configuration, prompts, and CLI overrides.

Method design: inputs, outputs, and responsibilities

The public interfaces make the ownership and one-cycle processing contract explicit. Helper methods are private to the component that owns the relevant state.

Cycle order: generate/filter arrivals → check scaling/cooldown → advance each server that was already busy → record completions → dispatch requests from the queue front to idle servers → increment completed-cycle count. Newly assigned requests start ticking next cycle. For example, a five-cycle request dispatched after the cycle-0 processing step gets its five ticks in cycles 1 through 5 and then becomes idle.

Scaling and reporting

The user's starting server count is total capacity. It is split evenly between the two job pools, assigning an odd extra server to P; therefore at least two starting servers are needed. Each type is queued FIFO and only handled by its own servers. Each pool is scaled against its own waiting queue: at most one server is added or removed globally per scaling check. Thresholds are strict: scale up above 80 waiting requests per server, and scale down below 50. A shared configurable cooldown separates successful changes. Each type keeps at least one server, and only idle servers are removed.

Verbose mode logs completions, blocked requests, server scaling, and periodic queue/server snapshots. It omits routine accepted/dispatched request events, which can overwhelm a high-volume log. Quiet mode keeps console output to start/end summaries. Both modes write run statistics to the configured log, and console-only ANSI colors never enter the log file. End-of-run reporting separates queued and active requests from completed requests.
